# Прорыв плотины — визуализация зоны затопления

Интерактивная карта распространения волны прорыва по результатам расчёта
HEC-RAS 2D на ЦМР 5 м. Несколько сценариев, воспроизведение по времени,
отсчёт глубины под курсором. Работает как статический сайт — без сервера,
без тайлового бэкенда, без API-ключей.

## Почему так

GitHub Pages отдаёт только статику: TiTiler или GeoServer там не поднять.
Значит рендер должен происходить в браузере. Серия из десятков растров на
сценарий — это гигабайты float32, которые нельзя ни закоммитить, ни
загрузить в клиент.

Решение — сжать данные под задачу, а не под универсальность:

| шаг | что делает | эффект |
|---|---|---|
| обрезка | находит общий контур затопления по всем кадрам | убирает пустые поля растра |
| прореживание | 5 м → размер под экран (по умолчанию 1400 px) | 5–20× |
| квантование | float32 → uint8, 0 = сухо, 1..255 = глубина | 4× |
| атлас | кадры пакуются в WebP-листы 4096×4096 | 1 запрос на 20–30 кадров |

На демо-наборе: **~300 МБ исходных GeoTIFF → 3.1 МБ веб-ассетов**
(3 сценария × 48 кадров). Глубина сохраняется с шагом `maxDepth/255` —
для 17 м это 7 см, что тоньше погрешности самой модели.

В браузере кадры распаковываются в `Uint8Array`, соседние интерполируются
по времени и пишутся в `<canvas>`, который MapLibre проецирует на карту как
`canvas`-источник. Никакого WebGL-шейдера: 900×558 px укладываются в
~4 мс на кадр, а карта остаётся обычной картой — с зумом, масштабной
линейкой и атрибуцией.

## Быстрый старт

```bash
pip install -r requirements.txt

python scripts/make_demo_data.py     # синтетический прорыв, если своих данных нет
python scripts/prepare.py --clean    # сборка ассетов в web/data/

cd web && python -m http.server 8000
```

Открыть <http://localhost:8000>. Пробел — пуск/пауза, стрелки на шкале
времени — по кадру, перетаскивание гидрографа — перемотка.

> Открывать `index.html` двойным кликом нельзя: `fetch` манифеста
> заблокирует CORS. Нужен любой локальный сервер.

## Импорт тайлового кэша RAS Mapper

Если вместо серии GeoTIFF у вас экспорт «Tile Cache» — файл `.db`, — он
подходит напрямую:

```bash
python scripts/import_rasmapper_tiles.py data/tilecache/sce1.db --list
python scripts/import_rasmapper_tiles.py data/tilecache/sce1.db \
    --name 01_vt-proryv --label "Верхне-Тобольское · прорыв плотины" --frames 72
python scripts/prepare.py --clean
```

`--group` объединяет сценарии одного водохранилища: в интерфейсе
появляется два уровня выбора — сначала объект, потом сценарий. Если группа
не задана, но подпись содержит `·`, `—` или `|`, она разбивается сама
(`«Каратомарское · паводок»`). При одной группе блок выбора объекта
скрывается.

```bash
python scripts/import_rasmapper_tiles.py data/tilecache/vt_pavodok.db \
    --name 01_vt-pavodok --group "Верхне-Тобольское" --label "Максимальный паводок"
python scripts/import_rasmapper_tiles.py data/tilecache/vt_proryv.db \
    --name 02_vt-proryv  --group "Верхне-Тобольское" --label "Прорыв плотины"
python scripts/import_rasmapper_tiles.py data/tilecache/kt_pavodok.db \
    --name 03_kt-pavodok --group "Каратомарское"     --label "Максимальный паводок"
python scripts/import_rasmapper_tiles.py data/tilecache/kt_proryv.db \
    --name 04_kt-proryv  --group "Каратомарское"     --label "Прорыв плотины"
```

Внутри одного водохранилища переключение сценария **не трогает камеру и
удерживает позицию на шкале времени** — иначе паводок и прорыв не
сравнить: карта улетала бы, а отсчёт сбрасывался. Смена водохранилища,
наоборот, пересобирает вид и начинает с нуля.

Сами `.db` кладите в `data/tilecache/` — каталог `data/` целиком в
`.gitignore`, в репозиторий уходят только собранные ассеты. Импортёр
запускается по одному разу на файл; `--name` задаёт порядок в списке,
`--label` — подпись в интерфейсе (пишется в `label.txt` рядом с растрами).

Верх цветовой шкалы общий для всех сценариев, иначе их нельзя сравнивать
глазом, но подстраивается под самый глубокий из них: `rampMax` в
манифесте. Паводок и прорыв одной плотины окажутся в одной системе
отсчёта автоматически.

Внутри такого `.db` — SQLite вида MBTiles с дополнительной колонкой `time`
и уже **отрисованными** PNG: цвет там не значение, а картинка по легенде.
Но легенда линейна и записана в таблице `metadata`, поэтому пересчёт
обратим — скрипт находит канал с наибольшим размахом и решает
относительно него. Для шкалы 0–15 м точность выходит 5.9 см, то есть
практически та же, что у нашего собственного квантования.

Проверено на реальном кэше: 457 часовых срезов за 19 суток, зумы 2–12,
73 738 тайлов, **182 МБ → 1.8 МБ веб-ассетов** (60 кадров, 1400×899).

Два подводных камня:

- **Разрешение задаёт maxzoom кэша, а не ЦМР.** z12 на широте 52° — это
  23 м/пиксель, вчетверо грубее ЦМР 5 м. Скрипт считает нужный зум и
  предупреждает; для 5 м нужен maxzoom 15. Пересобрать кэш в RAS Mapper
  дешевле, чем потом жалеть о деталях поймы.
- **Раздавать тайлы «как есть» для анимации плохо.** 458 срезов × тайлы —
  это сотни тысяч файлов и сетевой запрос на каждый шаг времени: плавной
  перемотки не будет. Поэтому кэш и разворачивается обратно в растр, а не
  подключается напрямую.

Готовые слои легенды тоже читаются: срез `Max` в кэше — это огибающая
максимумов, `prepare.py` считает свою собственную и на неё не опирается.

## Свои расчёты

Разложите экспорт RAS Mapper по каталогам — один каталог на сценарий,
один файл на временной шаг:

```
data/raw/
├── 01_polnyy-proryv/
│   ├── Depth (24JAN2024 06 00 00).tif
│   ├── Depth (24JAN2024 06 05 00).tif
│   └── ...
├── 02_chastichnyy-proryv/
└── 03_postepennyy-razmyv/
```

Имя каталога становится подписью сценария: числовой префикс задаёт порядок
и в подпись не попадает (`01_polnyy-proryv` → «polnyy-proryv»). Дата и время
берутся из имени файла — понимаются форматы RAS Mapper
(`24JAN2024 06 00 00`) и ISO (`2024-01-24T06-00-00`). Если распознать не
удалось, кадры нумеруются по порядку.

Требования к растрам: один канал, глубина в метрах, NoData на суше
(`-9999` или `NaN`). CRS любая — скрипт перепроецирует в EPSG:3857 сам.

```bash
python scripts/prepare.py --clean --max-dim 1600 --max-frames 80
```

- `--max-dim` — длинная сторона кадра в пикселях. Больше 1800 не имеет
  смысла: рендер начинает пропускать кадры на слабых машинах.
- `--max-frames` — если шагов больше, скрипт равномерно прореживает серию.
- `--format webp|png` — по умолчанию `webp`, он на 6–22 % меньше PNG и
  побитово ему равен. `png` — если нужна совместимость с чем-то древним.

### Почему не сжатие с потерями

Соблазн очевиден: на серии кадров H.264 или WebP q75 дают файл в 20 раз
меньше. На проверке это оказалось ловушкой.

| формат | «гладкие» данные | реальная текстура | ошибка |
|---|---|---|---|
| WebP lossless | 1.0 МБ | 3.5 МБ | нет |
| H.264 crf20 | 0.06 МБ | 1.14 МБ | 16 см средн., 2.0 м макс. |
| WebP q75 | 0.12 МБ | 0.28 МБ | 29 см средн., 2.4 м макс. |

Двадцатикратный выигрыш живёт только на искусственно гладких полях. Как
только в данных появляется текстура настоящего рельефа, преимущество
видеокодека над lossless практически исчезает — а платить за него
приходится кромкой затопления: H.264 crf20 на тестовом сценарии **залил
водой 213 тысяч сухих пикселей** (5.3 км²) и осушил 36 тысяч мокрых.
Для карты, у которой единственная по-настоящему важная линия — граница
затопления, это неприемлемо.

### Если нужны точные значения

Кадры квантованы в uint8: шаг `maxDepth/255`, для 17 м это 7 см. Если
карта должна отдавать инженерные отсчёты, а не картинку, разумнее
положить рядом **COG float32** и читать его через `geotiff.js`. На том же
сценарии это 8.3 МБ против 1.0 МБ — в 8 раз дороже, зато исходные
значения, стандартный формат и открывается в QGIS без конвертации.

Порог «сухо/мокро» — константа `WET_THRESHOLD` в начале `prepare.py`,
по умолчанию 5 см.

## Что считается по дороге

Помимо кадров `prepare.py` кладёт в `web/data/`:

- `*_maxdepth.png` — огибающая максимальных глубин за весь период.
  Показывается кнопкой «Максимум».
- `*_arrival.png` — **время добегания**: индекс кадра, в котором пиксель
  залился впервые. В интерфейсе пока не используется, но посчитан и лежит
  в манифесте — это готовый третий слой, если карта пойдёт в реальную
  работу по ЧС.
- гидрограф площади затопления, средней и максимальной глубины по кадрам —
  это он рисуется в нижней полосе.

Площадь приводится к реальной: Меркатор растягивает её в `1/cos²φ`, на
широте 55° это ровно в три раза.

## Публикация

Ассеты (`web/data/`) коммитятся, исходные растры — нет: `data/` в
`.gitignore`. Пуш в `main` запускает workflow, который выкладывает `web/`
на Pages. В настройках репозитория нужно один раз выставить
**Settings → Pages → Source → GitHub Actions**.

Лимиты GitHub — 100 МБ на файл и мягкий 1 ГБ на репозиторий. При
разумных `--max-dim` уложиться легко. Если ассеты всё же перевалят за
сотню мегабайт, положите их в GitHub Releases или на Cloudflare R2 и
поменяйте базовый путь в `app.js` — формат читается по обычному HTTP.

## Тест интерфейса

Логика выбора проверяется без браузера — на настоящем `manifest.json`,
в jsdom, с заглушками только для MapLibre и распаковки атласов:

```bash
npm install --no-save jsdom
node tests/ui.test.js
```

Проверяется, что группы собираются из `group.txt`, что внутри
водохранилища камера остаётся на месте, а позиция на шкале переносится
пропорционально (кадр 3 из 36 → кадр 5.06 из 60), и что при смене
водохранилища вид пересобирается.

## Известные ограничения

- Подложка — CARTO Dark Matter, публичный демо-эндпоинт. Для продакшена
  возьмите собственные тайлы или подписку.
- Между кадрами идёт линейная интерполяция глубины. Она сглаживает
  движение фронта, но это интерполяция, а не досчёт гидравлики: в момент
  прихода волны реальный фронт круче.
- Квантование обнуляет всё мельче `WET_THRESHOLD`. Для расчётов берите
  исходные GeoTIFF, эта карта — для чтения и показа.
- `make_demo_data.py` не является гидравлической моделью. Это кинематическая
  волна по синтетической долине, нужная только чтобы репозиторий собирался
  без реальных расчётов.

## Структура

```
scripts/prepare.py         пайплайн: GeoTIFF → WebP-атласы + manifest.json
scripts/import_rasmapper_tiles.py  тайловый кэш .db → GeoTIFF
scripts/make_demo_data.py  генератор синтетического набора
web/index.html             разметка
web/style.css              палитра и типографика
web/app.js                 распаковка, рендер, гидрограф, шкала
web/data/                  собранные ассеты (коммитятся)
tests/ui.test.js           прогон интерфейса в jsdom
data/raw/                  исходные растры (в .gitignore)
```
